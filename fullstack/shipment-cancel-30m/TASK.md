## 业务规则与接口

`GET /api/shipments` 返回 HTTP 200 和 `{ "shipments": [...] }`。每条运单包含 `id`、`recipient`、`status`。`GET /health` 只检查环境是否启动，不代表业务正确。

`POST /api/shipments/:id/cancel` 无需请求体，必须以**服务端当前状态**为依据：

| 当前情况 | HTTP 状态 | JSON 响应 | 数据变化 |
| --- | --- | --- | --- |
| 待发货 `ready` | 200 | `{ "shipment": { "id": "S1001", "recipient": "Alex Chen", "status": "cancelled" } }` | 该运单变为已取消 |
| 已取消 `cancelled`，包括重复请求 | 200 | 同结构的当前运单 | 保持已取消，重复操作视为成功 |
| 已发货 `shipped` | 409 | `{ "code": "INVALID_STATUS", "message": "已发货运单不能取消" }` | 保持已发货 |
| 运单不存在 | 404 | `{ "code": "SHIPMENT_NOT_FOUND", "message": "运单不存在" }` | 不改变任何运单 |

错误 `code` 与 HTTP 状态按表返回，`message` 可用同义中文。取消只改变目标运单的 `status`；不删除记录、不修改收件人、不影响其他运单。成功后再次查询列表或刷新页面，应能看到服务端保存的状态。

页面要求：

- 只有待发货运单提供取消入口；已有骨架已处理初始渲染。
- 点击后调用真实后端接口。等待响应期间给出处理中反馈，防止同一运单重复提交；请求结束后恢复可操作状态。
- 成功后根据服务端结果更新页面并提示成功，已取消运单不再显示取消入口。可以使用响应中的运单更新本地列表，也可以重新查询列表。
- HTTP 失败或网络失败时显示可理解的错误，保持当前运单状态，允许重试。不得在请求失败时显示取消成功，也不能只在浏览器里改状态。
